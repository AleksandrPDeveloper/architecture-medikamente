## Список проблемных зон

### Список процессов компании подлежащих обеспечению безопасности данных
1. Регистрация пациента
2. Приём пациента
3. Хранение персональных данных
4. Хранение медицинских данных
5. Назначение и передача информации о лечении
6. Взаимодействие с лабораториями
7. Доступ врача к истории болезни
8. Выдача результатов пациенту анализа пациенту
9. Архивирование и удаление данных
10. Доступ администраторов к персональным данным
11. Хранение платежной информации пациента
12. Открытый доступ без разграничения прав между сотрудниками компании
13. Физический сервер внутри компании
14. Передача персональной информации по внутренней почте

### Проблемные зоны
1. Взаимодействие с общим хранилищем информации без разграничений прав доступа,
по сути вся информация перс. данные, мед. данные, анализы, карты пациентов
хранятся в общих папках. Это значит что в целом, любой доктор может посмотреть любого пациента,
как и администратор и работник слада и т.д.
2. Даже при условии какого то разделения по папкам и прав доступа,
файлы можно скопировать удалить изменить, так же данные хранятся не в зашифрованном виде
3. Данные не передаются в зашифрованном виде.
4. Очень много ручных процессов, требующих автоматизации, повышается вероятность ошибки
при заполнении администратором и другими сотрудниками информации о пациенте.
5. Нет централизованного управления хранилищем данных, если пациент просит удалить информацию
о себе это будет весьма трудно.
6. Нет системы бэкапирования данных, в случае ошибки можно потерять всё, в том числе необходимую информацию,
для лечения пациента в единственном экземпляре.
7. Поскольку сервер находится в этом же здании, значит нет возможности распределить данные, по другим ЦОД,
для повышения отказоустойчивости.
8. Если физический доступ в ЦОД не ограничен, то сервера могут просто забрать, 
или получить к ним не санкционированный доступ.
9. Обмен между лабораториями не настроен, данные передаются и хранятся в не защифрованном виде,
скорее всего передаются или через публичные мессенджеры или копируются непосредственно в офисе компании.
10. Все базы данных 1с файловые, не зашифрованные, и без бэкапов, возможен риск потери, 
бухгалтерской и платежной информации. Риск потери базы ТМЦ не так критичен,
однако вызывает задержки в работе и постановке оборудования на учёт.
11. Аналогично перс данным, файловые БД можно забрать или изменить.
12. Передача информации по внутренней почте тоже может не контролироваться, что повышает риск утечки персональных данных.
13. Нет централизованной системы фиксации разрешений прав на управление данных пациентами.
14. Процесс поиска информации по пациенту может быть не прозрачным, и отсутствует аудит изменений,
как при ошибках, так и при вредительских действиях.
15. В связи со сбором и хранением данных, вручную пользователю не очевидно какой,
доступ к данным сейчас он предоставил организации, а управление перс. данными вообще не представляется возможным.
16. Возможна передача и сбор избыточных данных между процессами

### Что можно улучшить
1. Минимизация собираемых данных. 
2. Шифрование данных в хранении и передаче. 
3. Аутентификация и авторизация доступа. 
4. Логирование доступа и действий. 
5. Регулярное резервное копирование. 
6. Политика хранения и удаления данных. 
7. Защита интеграций (API, файлы, каналы связи).

### Примерный шаблон базовых ролей.

| Категория данных                                                            | Примеры                                                                       | Методы защиты                                                                     |
|-----------------------------------------------------------------------------|-------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| Персональные данные                                                         | ФИО, дата рождения, адрес, телефон, e-mail                                    | Шифрование в БД (AES-256), обезличивание при аналитике, контроль доступа          |
| Медицинские данные                                                          | Диагнозы, результаты анализов, медицинская карта                              | Шифрование в хранении и передаче, доступ по ролям, обезличивание для исследований |
| Финансовые данные                                                           | Счета, реквизиты, платежи                                                     | Шифрование (в т.ч. TLS 1.3 при передаче), токенизация                             |
| Данные авторизации                                                          | Логины, хеши паролей, токены доступа                                          | Хеширование паролей (bcrypt/Argon2), TLS 1.3, ограничение срока жизни токенов     |
| Складские/учётные данные                                                    | Инвентаризация, оборудование                                                  | При передаче — TLS 1.3, при хранении — контроль доступа, опционально шифрование   |
| Лог-файлы с чувствительными данными                                         | Журналы операций с идентификаторами пациентов                                 | Обфускация/маскирование ID, хранение в отдельном зашифрованном репозитории        |


### Пример тэгов:
PDL — Personal Data Level (персональные данные)
MDL — Medical Data Level
FDL — Financial Data Level
LS — чувствительные логи
PUB — общедоступные данные

### Внедрение
На уровне БД: добавить столбец data_tag или метаданные в схему.
На уровне ETL/интеграции: при загрузке в хранилище данные автоматически получают тег по правилу.
На уровне API: передача только тех данных, которые разрешены текущей ролью для данного тега.

### Инструменты:
Apache Atlas — для метаданных и тегирования в хранилище.
Collibra — для управления каталогом данных и тегами.
Если бюджет минимальный — хранение тегов в отдельной службе (PostgreSQL + REST API для проверки прав).

### Список инструментов, способов и мер защиты для потоков данных
Список инструментов, способов и мер защиты для потоков данных

| Этап                           | Меры                                                                               |
|--------------------------------|------------------------------------------------------------------------------------|
| Хранение данных                | AES-256 шифрование, Transparent Data Encryption, ограничение прав (RBAC)           |
| Передача данных                | TLS 1.3, VPN между филиалами, S/MIME  для почты                                    |
| Работа с файлами               | DLP-система, шифрование на уровне файловой системы / на уровне дисков              |
| Резервное копирование          | Шифрованные бэкапы, хранение в другом ЦОД                                          |
| Логи                           | Маскирование идентификаторов, раздельное хранение в защищённой системе логирования |
| Доступ к данным                | Централизованное управление доступом (Keycloak/LDAP), MFA                          |
| Взаимодействие с лабораториями | Защищённые каналы (SFTP, HTTPS API с JWT), шифрование файлов                       |
